### 2.1 Python 工程：先让项目跑起来

> [!question] 这一块复习时只问三件事
> 1. 「能跑起来」这份合同里必须有哪四样东西？（解释器版本 / 依赖清单 / 锁文件 / 启动方式）
> 2. `uv run` 替你走完了哪三步？为什么它比「`source .venv/bin/activate` 再 `python`」更不容易出错？
> 3. `git push -u` 里的 `-u` 做了什么？不做会怎样？
>
> 答不出就往下读对应小节，读完合上，把答案口述一遍。

#### 2.1.1 为什么「能跑起来」排在「写得漂亮」前面

工程不是一份放在你电脑里的代码，而是一份**别人也能复现的合同**。合同里至少要有四样东西：

1. **解释器版本**：这个项目用 Python 3.12，不是「我这能跑」的某个 3.13。
2. **依赖清单**：项目直接依赖哪些包，各自什么版本。
3. **锁文件**：把间接依赖也钉死，保证今天和三个月后装出来一样。
4. **启动方式**：一条命令能跑，而不是「你先这样，再那样」。

实习第一天最常做的事就是：

```text
拿到仓库地址 → git clone → 装依赖 → 跑测试 → 改一行 → 提 PR
```

这个动作每天重复五遍。你不需要第一天就写出漂亮架构，但必须让这条链走通；否则卡在装依赖上，问人都问不到点上——因为你连「哪一步、什么命令、完整报错」都说不清。

> [!important] `.venv` 存在的全部理由
> 系统级 Python 只有一套全局 `site-packages`。项目 A 要 `requests==2.31`、项目 B 要 `2.32`，后装的会把先装的覆盖掉，或者至少互相污染。`.venv` 让每个项目有自己的 `site-packages`，解释器可以共用，包互不干扰。
>
> `.venv` 不是「复制一份 Python」，而是「项目专属的包目录 + 指向解释器的链接」。它**不进 Git**，删了可以用 `uv sync` 重建。

#### 2.1.2 装 uv 和 Python 3.12

```bash
brew install uv
uv --version
```

预期看到类似：

```text
uv 0.13.5 (Homebrew 2026-10-22 aarch64-apple-darwin)
```

版本号不必一样，能看到 `uv x.y.z` 就说明命令进了 `PATH`。如果提示 `zsh: command not found: uv`，先开一个新终端；还不行就补 Homebrew 的路径：

```bash
eval "$(/opt/homebrew/bin/brew shellenv)"
```

> [!note] `PATH` 是什么，`which` 在查什么
> `PATH` 是一串用冒号隔开的目录。你敲 `uv`，shell 并不会「全局搜索」，而是按 `PATH` 的顺序，从左到右找第一个叫 `uv` 的可执行文件，找到就执行，找不到就 `command not found`。
>
> ```bash
> echo $PATH | tr ':' '\n'   # 一行一个目录，看顺序
> which uv                   # 只搜 PATH，返回第一个命中
> which -a python3           # 所有命中，常能看到 /usr/bin 和 Homebrew 两套
> type cd                    # 内建、别名、函数也能认出来
> ```
>
> Homebrew 在 Apple Silicon 上把程序装进 `/opt/homebrew/bin`。这个目录在不在 `PATH` 里，取决于当前 shell 启动时读到的配置；`brew install` 只改了磁盘，不改已经开着的终端——所以装完要开新终端，或者 `eval "$(brew shellenv)"` 重新加载。
>
> 还有一层缓存：shell 会记住命令路径。刚装完仍提示找不到时，`hash -r`（zsh 也可 `rehash`）清掉缓存再试。

接着装解释器并确认：

```bash
uv python install 3.12
uv python list
```

`uv python list` 里要能找到 `cpython-3.12.x`，并且后面没有 `download available`。`uv` 会把托管解释器放在自己的目录里，不覆盖系统 `python3`。具体装在哪，`uv python dir` 直接打印路径；`uv python list --only-installed` 只看已装的。

#### 2.1.3 建项目，跑出第一行

```bash
uv init --python 3.12 py-practice
cd py-practice
```

> [!warning] `uv init` 的模板会随版本变
> 老版本会生成 `main.py`；uv 0.13 默认生成 `src/py_practice/__init__.py`，**没有** `main.py`。所以不要赌模板，统一手动建一个 `main.py`，后面的命令才稳定。

```bash
cat > main.py <<'PY'
def main():
    print("hello")


if __name__ == "__main__":
    main()
PY

uv run main.py
```

预期输出：

```text
Using CPython 3.12.x interpreter at: ...
Creating virtual environment at: .venv
hello
```

只要最后一行是 `hello` 就算跑通。`uv run` 会自动做三件事：找 `.python-version` 指定的解释器 → 没有 `.venv` 就建 → 按 `pyproject.toml` / `uv.lock` 同步依赖，然后执行命令。它比「先 `source .venv/bin/activate` 再 `python`」少一步，也不会出现「忘了激活，装到全局去了」。

项目里几个文件的分工：

| 文件/目录 | 作用 | 要不要进 Git |
| --- | --- | --- |
| `pyproject.toml` | 项目名、Python 版本要求、直接依赖 | 要 |
| `.python-version` | 钉住这个项目用哪个 Python | 要 |
| `uv.lock` | 所有依赖的精确版本，保证可复现 | 要 |
| `.venv/` | 本项目实际安装的包和解释器链接 | **不要** |
| `src/py_practice/` | uv 0.13 默认生成的包目录 | 要 |
| `main.py` | 本项目的入口文件 | 要 |

`uv init` 在 0.13 里通常已经帮你 `git init` 了，分支一般就是 `main`。先检查：

```bash
git status
git branch --show-current
```

如果报 `not a git repository`，再执行 `git init -b main`。如果分支是 `master`，执行 `git branch -M main`。

#### 2.1.8 Git 的四个区与忽略规则

`git add` / `commit` / `push` 之所以容易混，是因为它们各推进一步，而不是同一件事的三个名字。先记住四个格子：

```text
工作区                暂存区(index)          本地库(.git)          远程(origin)
你改的文件  --add-->  下次提交的快照  --commit-->  提交历史  --push-->  GitHub
```

| 区 | 里面是什么 | 谁把它填满 | 怎么看 |
| --- | --- | --- | --- |
| 工作区 | 磁盘上正在编辑的文件 | 编辑器、`>`、`cp` | `git status`、`git diff` |
| 暂存区 | 下一次 commit 要包含的内容 | `git add` | `git diff --staged`、`git status` |
| 本地库 | 一次次的 commit 快照 | `git commit` | `git log --oneline` |
| 远程 | GitHub 上的副本 | `git push` | 网页、`git log origin/main` |

三条 diff 各看一段：

```bash
git diff            # 工作区 vs 暂存区：改了但还没 add 的部分
git diff --staged   # 暂存区 vs 最后一次 commit：add 了但还没 commit 的部分
git diff HEAD       # 工作区 vs 最后一次 commit：上面两段合起来
git diff --stat     # 只看哪些文件、各改了几行
```

`git status` 的短格式 `XY` 也按这个顺序读：X 是暂存区相对 HEAD，Y 是工作区相对暂存区。`??` 未跟踪，` M` 改了没 add，`M ` 已 add，`MM` 两段都有改动。

**`.gitignore` 按行写模式，不是按文件写路径**：

| 写法 | 匹配 | 注意 |
| --- | --- | --- |
| `*.log` | 任意目录下的 `.log` | 对已跟踪文件无效 |
| `/build/` | 只在仓库根下的 `build` 目录 | 开头 `/` 锚定根 |
| `build/` | 任意层级的 `build` 目录 | 结尾 `/` 只匹配目录 |
| `**/tmp` | 任意深度 | `**` 跨目录 |
| `!keep.log` | 取消上一条的忽略 | 顺序重要，放在后面 |

一个够用的 `.gitignore`：

```gitignore
.venv/
__pycache__/
*.py[cod]
.DS_Store
.env
```

> [!warning] 已经 commit 过的文件，再加 ignore 不生效
> ignore 只管「未跟踪」文件。`.venv/` 如果已经被跟踪，先用 `git rm -r --cached .venv` 把它从暂存区拿掉（磁盘文件不删），再 commit。验证：`git check-ignore -v .venv` 会打印命中的规则和行号。
>
> 空目录 Git 不跟踪；要保留目录结构，放一个 `.gitkeep`。

闭卷默写：画出四个区并标出 add / commit / push 各推哪一步；三条 diff 各看哪两段；写出 `.gitignore` 五行。

#### 2.2.1 先建一个安全的练习场

不要在家目录根上练 `rm -r`。先建一个专用目录：

```bash
mkdir -p ~/ew-lab/day1
cd ~/ew-lab/day1
pwd
```

`pwd` 输出的是**绝对路径**，例如 macOS 上是 `/Users/jionglin/ew-lab/day1`，Linux 上是 `/home/用户名/ew-lab/day1`。看到它，你才知道后面的 `rm -r` 到底会删哪。

三个路径符号：

| 写法 | 含义 | 例子 |
| --- | --- | --- |
| `.` | 当前目录 | `cp ./a.txt ./b.txt` |
| `..` | 上一级目录 | `cd ..` |
| `~` | 家目录 | `cd ~/ew-lab` |

绝对路径以 `/` 开头，任何时候都指同一个位置；相对路径不以 `/` 开头，跟着当前目录走。路径里有空格要加引号：`cd "My Folder"`。

#### 2.2.2 看位置：`pwd`、`cd`、`ls -la`

```bash
pwd
cd ~/ew-lab/day1
cd ..
cd -
cd
```

- `pwd`：打印当前工作目录的绝对路径。
- `cd 路径`：切过去。
- `cd`：不带参数，回家目录。
- `cd -`：回到上一次待过的目录，只记一步。
- `cd ..`：上一级。

```bash
ls
ls -l
ls -a
ls -la
ls -lh
```

| 参数 | 管什么 | 什么时候用 |
| --- | --- | --- |
| `-l` | 长格式：权限、所有者、大小、修改时间 | 看文件详情 |
| `-a` | 连 `.`、`..` 和 `.` 开头的隐藏文件一起列 | 找 `.gitignore`、`.venv`、`.env` |
| `-h` | 大小带 K/M/G 单位，通常和 `-l` 一起 | 看日志/数据文件多大 |
| `-t` | 按修改时间倒序 | 找刚改过的文件 |

`ls -la` 的每一列：

```text
drwxr-xr-x  5 user  staff  160 Nov  2 10:00 .
drwxr-xr-x  8 user  staff  256 Nov  2 09:59 ..
-rw-r--r--  1 user  staff   42 Nov  2 10:00 README.md
```

| 列 | 例子 | 含义 |
| --- | --- | --- |
| 1 | `drwxr-xr-x` | 文件类型 + 权限；`d` 是目录，`-` 是普通文件 |
| 2 | `5` | 硬链接数 |
| 3 | `user` | 所有者 |
| 4 | `staff` | 所属组 |
| 5 | `160` | 大小（字节）；加 `-h` 变 `160B` / `1.2K` |
| 6 | `Nov 2 10:00` | 最后修改时间 |
| 7 | `.` / `README.md` | 名字；`.` 当前目录，`..` 上一级 |

第 1 列那 9 位权限怎么拆、`755` 与 `644` 差在哪，见 §2.2.8。

#### 2.2.3 建、复制、改名、删除

```bash
mkdir -p demo/a/b
printf 'line1\nline2\nline3\nline4\nline5\n' > demo/a/b/log.txt

cp demo/a/b/log.txt demo/a/b/log.bak
cp -r demo demo-copy

mv demo/a/b/log.bak demo/a/b/log.old
mv demo/a/b/log.old demo/

rm demo/log.old
rm -r demo-copy
```

| 命令 | 做什么 | 关键点 |
| --- | --- | --- |
| `mkdir -p demo/a/b` | 连父目录一起建 | 不加 `-p`，`demo` 不存在就报 `No such file or directory` |
| `cp 源 目标` | 复制文件 | 复制目录要 `cp -r`；目标存在时默认覆盖 |
| `mv 源 目标` | 移动或改名 | 同一分区瞬间完成；目标存在时默认覆盖，且不提示 |
| `rm 文件` | 删除文件 | 没有回收站 |
| `rm -r 目录` | 递归删除目录 | `-r` 是 recursive；`-f` 是强制，不提示 |
| `rm -i` | 删除前逐个确认 | 不确定时加上 |

`mv` 既能改名也能移动：`mv a.txt b.txt` 是改名，`mv a.txt demo/` 是移动到 `demo/`。`rm -r` 之前先 `pwd` + `ls`，确认自己在练习场里。

#### 2.2.4 读文件：`cat`、`head`、`tail`

```bash
cat demo/a/b/log.txt
head -3 demo/a/b/log.txt
tail -3 demo/a/b/log.txt
```

- `cat`：一次输出整个文件，适合小文件。
- `head -3`：只看前 3 行；也可写 `head -n 3`。
- `tail -3`：只看后 3 行；`tail -f` 持续跟日志，`Ctrl+C` 退出。

`cat` 不要用来开大日志、图片、压缩包：大文件刷屏卡终端，二进制会喷乱码。大文件用 `less`，看头尾用 `head` / `tail`。

#### 2.2.5 管道与重定向

```bash
ls demo/a/b | wc -l
ls demo/a/b > list.txt
ls demo/a/b >> list.txt
cat list.txt
```

- `|`：把左边命令的标准输出，接到右边命令的标准输入。`ls | wc -l` 就是「列目录 → 数行数」，不产生中间文件。
- `>`：把标准输出写进文件；文件不存在就创建，**存在就先清空**。
- `>>`：追加到文件末尾，不清空。

> [!danger] `>` 是立即清空，不是「等命令跑完再覆盖」
> `echo hello > important.txt` 会先把 `important.txt` 截断为 0 字节，再写入。写错文件名，原内容当场没。
>
> 想防手滑，可以在当前 shell 开 `set -o noclobber`，这样 `>` 遇到已存在文件会拒绝；确实要覆盖时用 `>|`。

两个容易忽略的坑：

1. `ls > list.txt` 会把 `list.txt` 自己也列进去——因为 shell 先创建文件，`ls` 再读目录。
2. `wc -l` 数的是换行符。文件最后一行没有换行，结果会少 1。`ls | wc -l` 数的是「目录条目数」，包含子目录，不包含隐藏文件；要只数普通文件，用 `find . -maxdepth 1 -type f | wc -l`。

**三个流与退出码**：

| 流 | 编号 | 默认去哪 | 重定向 |
| --- | --- | --- | --- |
| 标准输入 | 0 | 键盘 | `< file` |
| 标准输出 | 1 | 终端 | `> file`、`>> file` |
| 标准错误 | 2 | 终端 | `2> file`、`2>&1` |

```bash
ls nope > out.txt 2> err.txt   # 正常输出与报错分开存
ls nope > all.txt 2>&1         # 合到一个文件；先指 1，再让 2 跟过去
ls nope 2>&1 > all.txt         # 错：2 先指向终端，1 后来才改，报错仍在屏幕
```

`2>&1` 的意思是「把 2 号流指向 1 号流当前指向的地方」，所以**先重定向 1，再合并 2**。顺序反了，2 还指着终端。

每条命令结束时都会留下一个退出码，`$?` 取到它：

```bash
true; echo $?        # 0，成功
false; echo $?       # 1，失败
nosuchcmd; echo $?   # 127，命令找不到
```

`&&` 前一条成功才跑后一条，`||` 前一条失败才跑后一条，`;` 无条件接着跑。管道 `a | b` 的退出码默认取**最后一条** `b`；想让任何一段失败都算失败，先 `set -o pipefail`。

#### 2.2.6 三个不可逆动作

#### 2.2.8 权限：9 位、755 与 644

`ls -l` 第一列不是装饰，是「文件类型 + 三组权限」：

```text
-rwxr-xr-x  1 user staff 42 Nov 2 10:00 run.sh
│└┬┘└┬┘└┬┘
│ │  │  └─ 其他人(other)：r-x
│ │  └──── 所属组(group)：r-x
│ └─────── 所有者(user)：rwx
└───────── 类型：- 普通文件  d 目录  l 符号链接
```

每组三位固定是 `r`（读 4）、`w`（写 2）、`x`（执行 1），没有就是 `-`。三组相加就是一个八进制数：`rwxr-xr-x` = 755，`rw-r--r--` = 644。

**`r/w/x` 对文件和目录不是一回事**：

| 位 | 对文件 | 对目录 |
| --- | --- | --- |
| `r` | 读内容 | 列出里面有哪些名字（`ls`） |
| `w` | 改内容 | 在里面新建 / 删除 / 改名条目 |
| `x` | 作为程序执行 | 进入 / 穿过（`cd`、访问里面的文件） |

目录只有 `r` 没有 `x`：能看见名字，但 `cd` 不进去，也读不了里面的文件。这是「权限明明给了却打不开」的头号原因。

**数字法**（最常用）：

| 数字 | 权限 | 典型用途 |
| --- | --- | --- |
| 755 | `rwxr-xr-x` | 目录、可执行脚本：自己能改，别人能进能读 |
| 644 | `rw-r--r--` | 普通文件、配置：自己能改，别人只读 |
| 600 | `rw-------` | 私钥、`.env`：只有自己能读写 |
| 700 | `rwx------` | 私有目录 |
| 777 | `rwxrwxrwx` | **不要用**：任何人都能改，等于把门敞开 |

```bash
chmod 755 demo
chmod 644 demo/a/b/log.txt
chmod 600 ~/.ssh/id_ed25519
chmod +x run.sh          # 符号法：给所有人加执行位
chmod u+x run.sh         # 只给所有者加
chmod go-w note.txt      # 去掉组和其他人的写权限
chmod -R 755 demo        # 递归；会把目录里的普通文件也变成可执行，慎用
```

`chmod -R 755` 的坑：目录要 `x`，普通文件通常不要 `x`。批量修更稳的写法是分开：

```bash
find demo -type d -exec chmod 755 {} \;
find demo -type f -exec chmod 644 {} \;
```

**新建文件的默认权限由 `umask` 决定**：文件从 `666` 开始、目录从 `777` 开始，减掉 `umask` 里禁止的位。macOS / Linux 常见 `umask 022`，于是文件 `666 & ~022 = 644`、目录 `777 & ~022 = 755`。直接敲 `umask` 就能看到当前值（输出 `0022`）。

> [!danger] 三个权限相关的常见事故
> 1. `chmod 777` 解决不了「权限不足」，只会把问题扩大；先看 `ls -l` 是哪一位不对。
> 2. 脚本报 `Permission denied`，先确认有没有 `x` 位；临时跑用 `bash run.sh`，长期用 `chmod +x`。
> 3. 改别人的文件才需要 `sudo chown`；`sudo chmod` 用错会把系统文件权限改坏，而且没有撤销。

macOS 的 `ls -l` 第一列末尾偶尔多一个 `@` 或 `+`：`@` 是扩展属性（如下载标记），`+` 是 ACL，`ls -le` 才看得到。它们不影响这 9 位的读法。

闭卷：把 `-rw-r-----` 翻译成「谁能读、谁能写、谁能执行」；说出 755 和 644 各给谁什么；解释「目录少了 `x` 位会怎样」。

### 2.3 哈希入门：把「查找」从 O(n) 降到 O(1)

> [!question] 这一块复习时只问三件事
> 1. 数组按下标取是 O(1)、按值查是 O(n)；哈希表凭什么把「按值查」也压到平均 O(1)？
> 2. Two Sum「先查后插」防的是哪个具体输入？换成「先插后查」会返回什么？
> 3. Contains Duplicate 的一行版能 AC，为什么还说不推荐？它丢了什么？
>
> 三题都能白板讲出来，再去 §7 写代码；讲不出就说明只是记住了代码，没记住机制。

#### 2.3.1 哈希表到底快在哪

数组按**下标**取元素是 O(1)，但「给你一个值，问它在不在」只能从头翻，是 O(n)。哈希表加了一层映射：

```text
key → hash(key) → 桶下标 → 直接跳到那个桶
```

查找时不再逐个比较，而是算一次哈希、跳到对应桶，所以平均 O(1)。不同 key 可能算出同一个桶，这叫**哈希冲突**；冲突多了，同一个桶里要挂链表或继续探测，最坏 O(n)。所以「O(1)」是平均情况，不是数学保证。

Python 里：

- `dict`：存「键 → 值」，例如 `值 → 下标`、`单词 → 次数`。
- `set`：只存键，用来判重、去重。
- 键必须**可哈希**：`int`、`str`、`tuple`（元素也都可哈希）可以；`list`、`dict`、`set` 不行。

代价是**占内存**：哈希表要预留空桶，负载因子高了还要扩容。哈希的本质就是「用空间换时间」。

Python 的 `dict` 从 3.7 起保证**插入有序**；扩容时按负载因子（约 2/3）翻倍重排。所以「平均 O(1)」是摊还结果，单次插入偶尔会 O(n)。

后端的缓存（Redis 的键值）、URL 去重、限流计数、路由表，全都建立在这个结构上。你不需要第一天就背底层，但要知道：**看到「查一个东西在不在」，先想哈希，不要先写两层循环。**

**30 秒估一下能不能跑**：n = 1e5 时，O(n) 约 1e5 次操作（毫秒级），O(n log n) 约 1.7e6（几十毫秒），O(n²) = 1e10（Python 里几百秒起步）。看到两层循环套在 1e5 上，先想能不能换哈希或排序。

#### 2.3.2 Two Sum：先暴力，再换哈希

题目：给数组 `nums` 和 `target`，返回两个下标，使 `nums[i] + nums[j] == target`，保证恰有一组解。

**第一步：暴力解**

```python
def two_sum_brute(nums: list[int], target: int) -> list[int]:
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []
```

外层固定 `i`，内层从 `i+1` 找 `target - nums[i]`。时间 O(n²)，空间 O(1)。n = 10,000 时大约 5,000 万次配对比较；量级一上去，接口就从 200ms 变成几十秒。

**第二步：把「找」换成哈希**

内层循环反复做同一件事：**在数组里找一个已知的值**。把「已经见过的值 → 下标」存进 `dict`，查找就从 O(n) 变成平均 O(1)。而且不用预先建表：边遍历、边查、边插，一趟结束。

```python
def two_sum(nums: list[int], target: int) -> list[int]:
    seen = {}                      # 值 -> 下标
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # 先查
            return [seen[need], i]
        seen[x] = i                # 查不到才插自己
    return []
```

手推 `nums = [2, 7, 11, 15]`、`target = 9`：

| i | x | need | 查 `seen` | 动作 | `seen` 状态 |
| --- | --- | --- | --- | --- | --- |
| 0 | 2 | 7 | 没有 | 插入 2→0 | `{2: 0}` |
| 1 | 7 | 2 | 有，下标 0 | 返回 `[0, 1]` | `{2: 0}` |

**为什么必须「先查后插」**：`nums = [3, 3]`、`target = 6`，如果先把当前 3 插进去，再查 `need = 3`，会查到自己，返回 `[0, 0]`，同一个元素用了两次。先查后插，`seen` 里只会有当前元素之前的元素，天然避免这个问题。

复杂度：

- 时间：O(n) 平均。每个元素查一次、最多插一次，哈希操作平均 O(1)；所有键都冲突时最坏 O(n²)。
- 空间：O(n)。最坏所有元素都进 `dict`。

易错点：

1. `seen` 存的是「值 → 下标」，不是「下标 → 值」；`need` 是值。
2. 返回下标，不是返回 `nums[i]` 和 `nums[j]`。
3. 查存在用 `if need in seen`，不要写 `if seen.get(need)`——下标 0 是假值，会漏。
4. 先查后插，别把当前元素先用两次。

完整题解、C++ 版本和同类题见 [[01-两数之和]]。

#### 2.3.3 Contains Duplicate：用 set 判重

题目：数组里任意值出现至少两次返回 `True`，全不重复返回 `False`。

**第一步：暴力解**

```python
def contains_duplicate_brute(nums: list[int]) -> bool:
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False
```

时间 O(n²)，空间 O(1)。n = 100,000 时是五十亿次级别的比较，必超时。

**第二步：哈希集合**

```python
def contains_duplicate(nums: list[int]) -> bool:
    seen = set()                   # 已经见过的值
    for x in nums:
        if x in seen:              # 见过 = 重复
            return True
        seen.add(x)                # 没见过才插入
    return False
```

时间 O(n) 平均，空间 O(n)。空数组、单元素数组天然返回 `False`，不用特判。所有键都冲突时，最坏退化到 O(n²)。

题目说「用 set 一行解决」，一行版是：

```python
def contains_duplicate_oneliner(nums: list[int]) -> bool:
    return len(set(nums)) != len(nums)
```

它能过，但**不早停**：`nums = [1, 1] + [0] * 100000` 时，循环版第二个元素就返回，一行版要把 10 万个 0 全部塞进 set。两者都是 O(n)，常数不同；面试时先写循环版，再补一行版，能讲清区别。

易错点：

1. 用 `list` 当 `seen`：`x in list` 是 O(n)，整套退回 O(n²)。必须用 `set`。
2. `set` 不能放 `list` / `dict`；遇到不可哈希元素要先转成 tuple 或换思路。
3. `set` 无序，不要依赖遍历顺序。
4. `len(set(nums)) != len(nums)` 对空数组、单元素都正确，但丢失了早停。

完整题解、C++ 版本和同类题见 [[02-存在重复元素]]。

#### 2.3.4 两题的共同模板

```python
seen = {}          # 需要下标/计数时用 dict
# 或
seen = set()       # 只判在不在时用 set

for i, x in enumerate(nums):
    # 1. 算 need（如果需要）
    # 2. 查 seen
    # 3. 命中就返回
    # 4. 没命中就存进去
```

| 题型 | 容器 | 存什么 | 查什么 |
| --- | --- | --- | --- |
| 两数之和 | `dict` | 值 → 下标 | `target - x` |
| 判重 | `set` | 已见的值 | `x` |
| 计数 | `dict` | 值 → 次数 | `x` |
| 缓存 | `dict` | key → value | `key` |

复杂度对照：

| 操作 | `list` | `dict` / `set` |
| --- | --- | --- |
| 按值查找 | O(n) | O(1) 平均 |
| 按键/下标取 | O(1) | O(1) 平均 |
| 尾部插入 | O(1) 摊还 | O(1) 平均 |
| 中间删除 | O(n) | O(1) 平均 |
| 内存 | 小 | 大 |

更系统的 Python 哈希与集合用法，见 [[02-哈希与集合]]；底层概念卡见 [[哈希表]]。

## 5. 常见报错（病例库）

> [!tip] 复习用法
> 遮住「处理」列，先说出你当时是怎么解决的，再对照。同一行错两次，就把这条抄进 §4.1 的报错表——那是你的个人病历。

| 报错 | 最可能的原因 | 处理 |
| --- | --- | --- |
| `zsh: command not found: uv` | Homebrew 的 bin 不在当前 shell 的 `PATH` | 开新终端；或 `eval "$(/opt/homebrew/bin/brew shellenv)"` |
| `No such file or directory: main.py` | `uv init` 新模板没有 `main.py`，或不在项目根目录 | `pwd`、`ls` 确认位置；按 2.1.3 手动建 `main.py` |
| `fatal: not a git repository` | 当前目录不是仓库根，或还没 `git init` | `pwd` 确认；`git init -b main` |
| `Permission denied (publickey)` | SSH 公钥没加到 GitHub，或 `IdentityFile` 指错 | `ssh -T git@github.com`；按 [[01-GitHub账号与首次推送]] 查 `~/.ssh/config` |
| `! [rejected] main -> main (fetch first)` | 远端仓库不是空的，已有 README 等提交 | 最省事：删远端重建空仓库；或 `git pull --rebase origin main` 后再推 |
| `error: src refspec main does not match any` | 还没有提交，或本地分支叫 `master` | `git log --oneline` 看有没有提交；`git branch -M main` |
| VS Code 断点不生效 | 解释器选成了系统 Python | `Cmd+Shift+P` → `Python: Select Interpreter` → `.venv/bin/python` |

## 7. 自测

合上正文再点开答案。答不上来的，按每题标题里的 § 号回去看那一小节，看完关掉重答。

<details>
<summary>Q1 · §2.2.2：`ls -l` 和 `ls -a` 各管什么？`ls -la` 呢？</summary>

`-l` 是长格式，显示权限、所有者、大小、修改时间；`-a` 是 all，连 `.`、`..` 和 `.` 开头的隐藏文件一起列。`-la` 就是两者叠加：既看详情，也不漏隐藏文件。
</details>

<details>
<summary>Q2 · §2.1.1：为什么 `.venv/` 不能提交到 Git？</summary>

`.venv` 里是当前机器、当前系统装出来的包和解释器链接，体积大且不可跨平台复用。项目只需要提交 `pyproject.toml`、`.python-version` 和 `uv.lock`；别人 clone 后 `uv sync` 就能重建自己的 `.venv`。
</details>

<details>
<summary>Q3 · §2.2.5：`>` 和 `>>` 的区别是什么？</summary>

`>` 覆盖写：文件存在就先清空，再写入；`>>` 追加写：保留原内容，在末尾继续写。改配置/日志时先想清楚用哪个，`>` 用错会直接丢数据。
</details>

<details>
<summary>Q4 · §2.3.2：Two Sum 为什么必须「先查后插」？</summary>

`seen` 里只能放当前元素之前的元素。如果先把当前元素插进去，再查 `target - x`，当 `target = 2x` 时会查到自己，同一个下标被用两次。`[3,3], target=6` 就是典型：先插后查会返回 `[0,0]`，先查后插返回 `[0,1]`。
</details>

<details>
<summary>Q5 · §2.3.3：Contains Duplicate 为什么用 `set`，不能用 `list` 当「已见」容器？</summary>

`x in list` 要逐个比较，是 O(n)；外层再遍历 n 次，整体退回 O(n²)。`x in set` 平均 O(1)，整体 O(n)。数据量一大，list 版会超时。
</details>

<details>
<summary>Q6 · §2.1.3：`uv run main.py` 和 `python main.py` 差在哪？</summary>

`uv run` 先用 `.python-version` 找解释器、缺 `.venv` 就建、按 `pyproject.toml` / `uv.lock` 同步依赖，再执行命令。`python main.py` 用的是 `PATH` 里那个 `python`——很可能是系统 3.13，依赖没装在那里就 `ModuleNotFoundError`；就算装上了，也是装到全局，污染别的项目。
</details>

<details>
<summary>Q7 · §2.3.1：哈希表「平均 O(1)」什么时候不成立？退化到多少？</summary>

大量键落进同一个桶时（哈希函数差，或有人恶意构造），桶里只能挂链表或继续探测，等于逐个比较，最坏 O(n)；所有键都冲突时，整体退化成 O(n²)。所以 O(1) 是平均情况下的期望，不是数学保证——这也是「用空间换时间」的代价。
</details>

<details>
<summary>Q8 · §2.2.5：`ls demo/a/b | wc -l` 数的是什么？什么时候会少 1？</summary>

数的是 `ls` 输出的行数，也就是目录里的条目数：含子目录，不含 `.` 开头的隐藏文件。`wc -l` 数的是换行符，最后一行没有换行就会少 1。「只数普通文件」要用 `find . -maxdepth 1 -type f | wc -l`。
</details>

<details>
<summary>Q9 · §2.2.8：`-rw-r-----` 谁能读、谁能写、谁能执行？目录少了 `x` 位会怎样？</summary>

所有者（user）能读能写、不能执行；同组（group）只能读；其他人什么都不能。数字是 640。目录少了 `x`，`ls` 还能列出名字，但 `cd` 进不去，也读不了里面的文件——「有 `r` 没 `x`」是最常见的「权限明明给了却打不开」。
</details>

<details>
<summary>Q10 · §2.1.8：Git 四个区是什么？`git diff` 和 `git diff --staged` 各看哪两段？</summary>

工作区 →（`git add`）→ 暂存区 →（`git commit`）→ 本地库 →（`git push`）→ 远程。`git diff` 看工作区 vs 暂存区（改了没 add），`git diff --staged` 看暂存区 vs 最后一次 commit（add 了没 commit）。
</details>

<details>
<summary>Q11 · §2.2.5：`> f 2>&1` 和 `2>&1 > f` 差在哪？`$?` 为 0 / 1 / 127 各说明什么？</summary>

`> f 2>&1` 先把 1 指向文件，再让 2 跟着 1，两条流都进文件；`2>&1 > f` 先把 2 指向终端，再改 1，报错仍打在屏幕。`$?`：0 成功，1 一般失败，127 命令找不到。
</details>

<details>
<summary>Q12 · §2.1.2：`PATH` 是什么？`which` 查的是什么？为什么装完要开新终端？</summary>

`PATH` 是冒号分隔的目录清单，shell 按顺序找第一个同名可执行文件。`which` 只在这个清单里找，返回第一个命中；`type` 还能认出别名和内建。`brew install` 只把文件写进 `/opt/homebrew/bin`，已经开着的 shell 不会重读配置，所以 `PATH` 里可能还没有这个目录——开新终端或 `eval "$(brew shellenv)"` 才会生效。
</details>

## 8. 工程四件套：碎片、复盘、交付、卡住

> [!question] 这一章为什么存在
> 周计划里这四块每天只占一行：默写 10–15 条命令、写三行日志、交付一个仓库、卡住就降级。一行字最容易被当成「顺手做一下」，结果每天都没做。这一章把四行字拆成可执行的标准：每块到底练什么、怎么练、做到什么算过。

### 8.1 碎片 20 分钟：命令按「动作」归类，不按字母背

**为什么 20 分钟够**：一次能记住的不是 30 条命令，而是 5 组、每组 5–7 条。把 30 条命令按「环境 / 项目 / Git / Linux / 管道」分组，每组是一个 chunk；20 分钟刚好够每组过一遍。散着背，30 条就是 30 个 chunk，一定记不住。

**命令的解剖**：`命令 [选项] [参数]`

```bash
ls   -la        demo
# │    │         │
# 动词 副词      宾语
```

选项回答「怎么干」，参数回答「对谁干」。记命令时三样一起记：`ls -la demo` 是「以长格式、含隐藏文件，列出 demo」，不是「ls 加 l 加 a」。

**词根表**（先记这 12 个，覆盖本周 80% 的选项）：

| 字母 | 词 | 意思 | 本周例子 | 易混 |
| --- | --- | --- | --- | --- |
| `-l` | long | 长格式 | `ls -l` | 和 `-a` 叠加成 `-la` |
| `-a` | all | 连 `.`、`..` 和隐藏文件一起列 | `ls -a` | 默认不显示 `.` 开头的文件 |
| `-h` | human | 人类可读的大小 | `ls -lh`、`du -sh` | 不是 help（help 是 `--help`） |
| `-r` | recursive | 递归 | `cp -r`、`rm -r` | 在 `sort`/`ls` 里是 reverse（倒序） |
| `-p` | parents | 连父目录一起建 | `mkdir -p a/b/c` | 在 `cp` 里是 preserve（保留属性） |
| `-f` | force | 强制、不提示 | `rm -f` | 危险，等于关掉刹车 |
| `-i` | interactive | 交互确认 | `rm -i`、`git add -i` | 和 `-f` 相反 |
| `-n` | number | 行号 / 不执行 | `grep -n`、`cat -n`、`git push -n` | 具体看命令 |
| `-v` | verbose / invert | 详细 / 反选 | `cp -v`、`grep -v` | 具体看命令 |
| `-t` | time | 按修改时间排序 | `ls -lt` | `find -type` 是长选项，不是 `-t` |
| `-R` | recursive（大写） | 递归（chmod/chown） | `chmod -R` | 大小写不同命令不同 |
| `--` | 长选项 | 全名 | `--help`、`--version` | 和单字母等价时优先用长的 |

**同一字母在不同命令里会变**：`-r` 在 `cp/rm` 是递归，在 `sort -r`/`ls -r` 是倒序；`-p` 在 `mkdir` 是 parents，在 `cp` 是 preserve。所以记「命令 + 字母」的配对，别记孤立的字母表。

**三遍法**（20 分钟怎么切）：

1. **读一遍（5 分钟）**：看 §3.1 的「命令 → 干什么」，每条读出声，重点读 `rm`、`mv`、`>` 这三条会出事故的。
2. **遮住默写（10 分钟）**：遮右列，写命令 + 一句用途；写完对照，错的画 ✗。
3. **终端敲一遍（5 分钟）**：在 `~/ew-lab/day1` 里把 ✗ 的命令真敲一次，看输出。手比眼记得牢。

**默写不是抄写**：抄 10 遍不如遮住写 1 遍。判断标准是「看到用途能写命令，看到命令能说用途」，两个方向都要过。

**终端里的记忆外挂**：

```text
Ctrl + R             # 反向搜索历史命令，敲 ls 就能翻到上次的 ls -la
!!                   # 重复上一条命令
!$                   # 上一条命令的最后一个参数
history | grep git   # 从历史里找 git 命令
```

这些不替代默写，但能让你在「想不起来」时不用重开教程。

**三个必踩的坑**：

1. `cp 目录 目标` 不加 `-r`：报 `omitting directory`，不是权限问题。
2. `mkdir a/b/c` 不加 `-p`：父目录不存在直接 `No such file or directory`。
3. `rm -rf` 的 `-f` 会吞掉所有确认；练习时先用 `rm -r`，看清再删。

**当天验收**：15 条命令 120 秒内默写，每条一句「干什么」；`cp`/`mkdir`/`rm` 三个坑能各说一条。

### 8.2 复盘与笔记：把「今天」变成「可检索的资产」

**三行日志，每行一个动作**：

| 行 | 回答什么 | 坏例 | 好例 |
| --- | --- | --- | --- |
| 学了什么 | 今天**能做什么**了 | 看了字符串方法 | 能用 `split` + `strip` 把 `" 2026-11-02, 47 "` 拆成日期和数字 |
| 卡在哪 | 哪个命令 / 哪行报错 / 已试什么 | Git 不熟 | `git push` 报 `! [rejected] (fetch first)`，已试 `git pull`，冲突不会解 |
| 明天第一件事 | 坐下 10 分钟内能开始的动作 | 学 Python | 跑通 `str_demo.py` 的 `split` 例子，再补 `strip` 去标点 |

坏例的共同点：写「感受」和「学科名」，不写「动作」和「对象」。一周后回看，坏例无法复原当时在干什么，好例可以直接接着做。

**笔记不是抄书，是检索线索**：一条能复习的笔记至少有三样——① 一个问题（「`>` 和 `>>` 差在哪」）；② 答案在哪（§2.2.5 / 命令表第 22 条）；③ 自己的例子（`ls > list.txt` 把 `list.txt` 自己也写进去了）。只有 ①② 是教程，加上 ③ 才是你的笔记。

**报错病例库，三列缺一不可**：

```markdown
| 报错原文 | 原因 | 处理 |
| --- | --- | --- |
| `! [rejected] main -> main (fetch first)` | 远端已有 README 提交，本地历史接不上 | 删远端重建空仓库；或 `git pull --rebase origin main` 再推 |
```

「报错原文」必须**逐字复制**，包括 `!`、路径、退出码。因为下次你搜的是原文，转述成「推送被拒绝」就搜不到了。原因写「机制」，不写「我粗心」；处理写「下次第一步敲什么」，不写「注意一下」。

**复盘四问**（周日用，平时三行就够）：

1. 哪里卡住？（具体到命令 / 小节）
2. 为什么卡？（缺前置知识 / 环境 / 题意没读懂）
3. 下周砍什么？（砍任务，不砍睡眠）
4. 保留什么？（有效的动作，继续做）

**间隔重复的节奏**：D1/D2/D4/D7/D15/D30 不是重读全文，是重答 §0 的 16+4 问；答不出的只回对应小节，看完合上口述。每轮只填 §10 一行，正文不动。

**反模式**：① 流水账（「今天学了 Git」）；② 只写「完成 / 未完成」；③ 把 AI 的解释整段粘贴，没有自己的例子；④ 错题只抄答案，不写「当时为什么那么想」。

**当天验收**：三条日志能让人照着复现你明天要做的第一步；两个报错有原文、原因、处理。

### 8.3 今日交付：`py-practice` 仓库的 Definition of Done

**Definition of Done 五条**（本周所有交付都按这个判）：

| # | 标准 | 反例 |
| --- | --- | --- |
| 1 | 能跑 | 只在 IDE 里点过 Run，终端里没跑过 |
| 2 | 能复现 | 换一台机器 / 新 clone 就缺文件、缺依赖 |
| 3 | 已提交 | 本地改完没 `git add`，或 commit 了没 push |
| 4 | 有说明 | README 只有标题，别人不知道先敲哪条 |
| 5 | 边界不崩 | 空输入 / 重名 / 无权限直接 traceback |

**Day 1 交付：`py-practice` 仓库**

不是「我本地能跑」，是「陌生人 clone 下来能跑」。验收命令（在任意空目录）：

```bash
cd /tmp
git clone git@github.com:SunJionglin/py-practice.git
cd py-practice
uv sync
uv run main.py        # 期望输出 hello
```

四步任何一步失败，都算没交付：

- clone 失败 → 仓库没建对 / SSH 没配（回 §2.1.5）。
- `uv sync` 失败 → `pyproject.toml` / `uv.lock` 没提交，或 `.venv` 被提交了。
- `uv run main.py` 找不到文件 → `main.py` 不在仓库根，或没提交。
- 输出不是 hello → 提交的是旧版本，`git log --oneline` 看一眼。

**提交不是「存盘」**：一次提交只做一件事。Day 1 至少两次：

```bash
git add .
git commit -m "init: uv project skeleton"
# 改完 main.py / README 后
git add -A
git commit -m "feat: print hello and add README"
```

`git log --oneline` 要能读出「先骨架、后功能」。`update`、`fix`、`111` 这种 message 等于没写。`git commit -am` 只对**已跟踪**文件生效；新建的 `README.md` 没 `git add` 过，`-am` 不会带上它。

**README 最少 5 行**：是什么 / 怎么装 / 怎么跑 / 输出示例 / 已知限制。别人先看 README 再看代码；README 缺「怎么跑」，代码写得再好也等于没交付。

**三个 false done**：① `.venv/` 被提交（仓库巨大且跨平台不可用）；② 只 `commit` 没 `push`（GitHub 上看不到）；③ README 写了但命令是错的（比不写更糟）。

**当天验收**：上面四步 clone 测试全过；`git log --oneline` ≥2 行且看得懂；README 五要素齐。

### 8.4 卡住怎么办：timebox、排错顺序、降级

**三个时间闸门**（到点就切换，不靠意志力）：

| 卡住的对象 | 闸门 | 到点动作 |
| --- | --- | --- |
| 一道算法题 | 20 分钟 | 看题解，关掉，默写一遍 |
| 一个学习块（语法 / 终端） | 30 分钟 | 跳过，记「遗留」，后面的块照常 |
| 环境（uv / venv / SSH） | 40 分钟 | 切系统 `python3 -m venv`，先让仓库跑通 |

**为什么必须 timebox**：卡住时学习曲线是平的，继续耗只增加挫败感；切换后大脑后台还在处理（incubation），第二天常会突然通。硬耗 2 小时不如记下报错、做完别的、周日集中补。

**排错顺序，从便宜到贵**：

1. **读最后一行**：`TypeError` / `ModuleNotFoundError` 是「什么错」，往上找 `File "...", line N` 是「在哪」。
2. **最小复现**：把问题缩到三行，`python3 -c '...'` 能复现再修。
3. **查假设**：`pwd`（在哪）、`which python3`（用的哪个解释器）、`python3 --version`、`echo $PATH`。一半的「玄学」是目录或解释器不对。
4. **搜原文**：去掉用户名 / 路径，保留引号和错误码；先看官方文档，再看 issue。
5. **问人**：带齐五样（见下）。

**问人带五样**（缺一样，对方只能猜）：

```text
1. 完整命令：uv python install 3.12
2. 完整报错：error: Failed to download ... SSL: CERTIFICATE_VERIFY_FAILED
3. 环境：macOS 15.2 arm64 / uv 0.5.11 / python3 3.13.1
4. 已试：brew upgrade ca-certificates，重启终端，仍报错
5. 期望：装完 uv python list 能看到 3.12
```

**降级不是放弃**：环境装不上，走系统 Python 路线（§2.1.7），Git 和算法照做；推导式写不出，先用 for 循环跑通再化简；函数不会拆，先复制成三段再包 `def`。降级的目标是「今天的主线不断」，不是「把标准降低」。

**遗留怎么写**：不写「环境没装好」，写「`uv python install 3.12` 报 `SSL: CERTIFICATE_VERIFY_FAILED`；已试 `brew upgrade ca-certificates`；周日补」。要能让周日的你一眼接着做。

**求助反模式**：只发「报错了」；截图不带命令；问「怎么学 Python」；同一问题问三个人但不贴报错。

**当天验收**：能说出「我现在卡在哪一步、下一步试什么、到几点还不行就降级」；遗留条目带命令和报错原文。
