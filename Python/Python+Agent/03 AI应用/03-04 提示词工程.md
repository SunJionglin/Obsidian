## 0. 速记

> [!tip] 五句话
> - 提示词是你发给模型的话；提示词工程是不断改它直到输出符合预期
> - 六要素：角色、任务、要求、示例、输出格式、风格
> - 结构化描述 > 堆形容词
> - 给一个例子（few-shot）往往比讲十句道理有效
> - 复杂任务拆成步骤，让模型一步一步来

## 1. 语法速查

### 1.1 六要素

| 要素 | 作用 | 示例 |
|---|---|---|
| 角色 | 限定知识面和语气 | 「你是一名高中历史老师」 |
| 任务 | 一句话说清要什么 | 「解释法国大革命的原因」 |
| 要求 | 拆步骤、给约束 | 「分政治、经济、思想三点」 |
| 示例 | 对齐输入输出格式 | 「输入：… 输出：…」 |
| 输出格式 | 方便程序解析 | 「输出 JSON，字段为 …」 |
| 风格 | 控制语气长度 | 「口语化，不超过 100 字」 |

### 1.2 通用模板

```text
你是一名<角色>。

任务：<一句话说明要做什么>。

要求：
1. <步骤或约束>
2. <步骤或约束>
3. <长度、语气、禁忌>

输出格式：<JSON / Markdown 表格 / 纯文本>

示例：
输入：<示例输入>
输出：<示例输出>
```

### 1.3 三种常见范式

| 范式 | 做法 | 适合 |
|---|---|---|
| Zero-shot | 只给任务，不给例子 | 简单、常见任务 |
| Few-shot | 给 1～3 个输入输出示例 | 格式固定、风格特殊 |
| CoT | 要求「一步一步思考」 | 推理、计算、多步任务 |

### 1.4 迭代方法

1. 先写最小可用提示词，跑一次。
2. 看输出哪里不对，只改一个变量。
3. 加约束、加反例、加格式要求。
4. 稳定后固化成模板，参数用变量替换。

## 2. 与 C++ 的差异

本节与 C++ 没有语法差异，但「接口」的思维方式完全不同：

| 维度 | C++ 函数 | 提示词 |
|---|---|---|
| 入参 | 类型固定、编译期检查 | 自然语言，运行期才知对错 |
| 出参 | 类型确定 | 自由文本，可能跑题 |
| 复用 | 函数签名不变 | 可复用，但换模型要重调 |
| 版本 | 代码版本固定 | 模型更新后效果会变 |
| 调试 | 断点、日志 | 改措辞、加例子、换模型 |
| 文档 | 头文件注释 | 提示词本身就是文档 |

## 3. 易漏点

- **重要信息放前面**：长提示词里，模型对开头和结尾更敏感。
- **`system` 定角色，`user` 放任务**：别把角色写进每一条 user 消息。
- **示例要和目标格式一致**：示例里用表格，输出才会是表格。
- **否定指令效果差**：「不要啰嗦」不如「每条不超过 20 字」。
- **温度影响稳定性**：要固定格式时调低 `temperature`。
- **上下文有限**：长文档要分段喂，或先摘要再提问。
- **模型会顺着错误前提编**：前提错了，它会一本正经地圆下去。

## 4. 易错点

> [!warning] 一次给太多任务
> 「写代码 + 写测试 + 写文档 + 翻译」混在一条里，每样都做不精。拆开。

> [!warning] 没有输出格式要求
> 模型自由发挥，程序没法解析。明确 JSON schema 或表格列名。

> [!warning] 示例和任务矛盾
> 示例是英文、任务是中文，输出风格会漂移。

> [!warning] 把敏感信息写进提示词
> 密钥、身份证、客户数据都会进入第三方服务。

> [!warning] 期望一次就完美
> 提示词是迭代出来的，第一版能达到 60 分就不错。

## 5. 自测

> [!question]- 把「给我讲一下 Python 的列表」改成结构化提示词。
> **答案**：
> ```text
> 你是一名 Python 讲师，读者有 C++ 基础。
> 任务：讲解 Python list 与 C++ vector 的差异。
> 要求：分「语法、内存模型、常用操作」三点，每点配一段代码。
> 输出格式：Markdown 三级标题 + 代码块，不超过 500 字。
> ```

> [!question]- few-shot 适合什么场景？
> **答案**：输出格式固定、风格特殊、零样本效果不稳定的场景，给 1～3 个示例最有效。

> [!question]- 为什么「不要啰嗦」不如「不超过 20 字」？
> **答案**：否定指令只说了不要什么，没给可执行的标准；正面约束可量化、可检查。
