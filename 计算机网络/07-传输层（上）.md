# 07 传输层（上）

> 网络层把包送到「主机」，但主机上跑着几十个程序——微信、浏览器、游戏。传输层负责**把数据交给正确的进程**，并决定「要不要保证可靠」。

## 7.0 先讲清楚：传输层在解决什么

一台电脑同时开着浏览器、微信、游戏。它们都在收发数据，可 IP 层只认「IP 地址」，不认「哪个程序」。

所以要给每个程序一个编号——**端口号**。IP 地址 + 端口 = 唯一确定「哪台机器上的哪个程序」。

```
网络层：主机 → 主机（IP）
传输层：进程 → 进程（IP + 端口）
```

这就叫**端到端**（end-to-end）：传输层只关心两端，中间的路由器不参与。

## 7.1 端口与复用/分用

| 端口范围 | 名称 | 说明 |
| --- | --- | --- |
| 0–1023 | 熟知端口 | 系统服务固定使用 |
| 1024–49151 | 登记端口 | 一般应用注册使用 |
| 49152–65535 | 客户端临时端口 | 客户端发起连接时临时分配 |

**常用端口（记住这些就够）**：

| 端口 | 服务 | 协议 |
| --- | --- | --- |
| 20 / 21 | FTP 数据 / 控制 | TCP |
| 22 | SSH | TCP |
| 23 | Telnet | TCP |
| 25 | SMTP | TCP |
| 53 | DNS | UDP（也可 TCP） |
| 80 | HTTP | TCP |
| 110 | POP3 | TCP |
| 443 | HTTPS | TCP |

**复用与分用**：

- **复用**：发送方多个进程的数据，都用同一个传输层协议（TCP/UDP）封装后交给网络层。
- **分用**：接收方根据端口号，把数据交给对应的进程。

## 7.2 UDP：简单到极致

**首部只有 8 字节**：

```
| 源端口 2B | 目的端口 2B | 长度 2B | 校验和 2B |
```

**特点**：

| 特点 | 含义 |
| --- | --- |
| 无连接 | 不用握手，直接发 |
| 不可靠 | 丢了不重传，错了不纠正 |
| 面向报文 | 应用给一个报文，UDP 原样发一个，不合并不拆分 |
| 无拥塞控制 | 网络再挤也照发（适合实时音视频） |
| 首部小 | 8 B，比 TCP 的 20 B 省 |

**校验和**：计算时要加一个 12 字节的**伪首部**（源 IP、目的 IP、协议号、UDP 长度），目的是顺便校验 IP 地址有没有被改错。伪首部只参与计算，不真的传输。

**什么时候用 UDP**：DNS 查询（一问一答，快）、视频直播（丢几帧没关系）、游戏（要低延迟）。

## 7.3 TCP：可靠、面向连接

| 特点 | 含义 |
| --- | --- |
| 面向连接 | 先握手建立连接，再传数据，最后挥手断开 |
| 可靠传输 | 序号 + 确认 + 重传，保证不丢不重不乱序 |
| 字节流 | 把数据看成连续的字节，没有报文边界 |
| 全双工 | 双方同时可以发和收 |
| 一对一 | 不支持广播/多播 |
| 流量控制 + 拥塞控制 | 根据接收方能力和网络状况调速 |

**首部 20 字节**（固定部分）：

| 字段 | 长度 | 作用 |
| --- | --- | --- |
| 源端口 / 目的端口 | 各 2 B | 定位进程 |
| 序号 seq | 4 B | 本报文段第一个字节的编号 |
| 确认号 ack | 4 B | 期望收到的下一个字节编号 |
| 数据偏移 | 4 bit | 首部长度，以 4 字节为单位（最小 5 = 20 B） |
| 控制位 | 6 bit | URG / ACK / PSH / RST / SYN / FIN |
| 窗口 | 2 B | 接收窗口，用于流量控制 |
| 校验和 | 2 B | 含伪首部 |
| 紧急指针 | 2 B | 配合 URG 使用 |

六个控制位各管什么：

| 位 | 含义 |
| --- | --- |
| URG | 紧急指针有效 |
| ACK | 确认号有效（连接建立后一直为 1） |
| PSH | 催促接收方尽快上交应用层 |
| RST | 重置连接（异常断开） |
| SYN | 请求建立连接 |
| FIN | 请求释放连接 |

## 7.4 三次握手

![[图/三次握手四次挥手.png]]

> 左边客户端、右边服务器，三条箭头就是三次握手，四条箭头是四次挥手。

```
1. 客户端 → 服务器：SYN=1, seq=x            （我想连你）
2. 服务器 → 客户端：SYN=1, ACK=1, seq=y, ack=x+1   （我同意，也想连你）
3. 客户端 → 服务器：ACK=1, seq=x+1, ack=y+1        （收到，开始吧）
```

**为什么要三次，不是两次**：

- 两次的话，服务器发完 SYN+ACK 就认为连接建立了，但它**无法确认客户端收到了自己的 SYN**。
- 第三次 ACK 让服务器确认「客户端的收发能力都正常」，双方都确认了对方的收发能力，才算可靠。
- 还有一个作用：防止**已失效的连接请求**突然到达服务器，造成服务器白白建立连接。

**SYN 洪泛攻击**：攻击者大量发 SYN 不回 ACK，服务器半连接队列被占满。防御手段之一是 **SYN Cookie**（不立即分配资源，用哈希算出的序号验证）。

## 7.5 四次挥手

```
1. 客户端 → 服务器：FIN=1, seq=u          （我没数据发了）
2. 服务器 → 客户端：ACK=1, ack=u+1        （知道了）
3. 服务器 → 客户端：FIN=1, ACK=1, seq=w, ack=u+1  （我也发完了）
4. 客户端 → 服务器：ACK=1, ack=w+1        （收到）
```

**为什么四次而不是三次**：TCP 是全双工的，一方说「我不发了」不代表另一方也发完了。服务器收到 FIN 后可能还有数据要发，所以先回一个 ACK，等自己发完再发 FIN——这就拆成了两次。

**TIME_WAIT 为什么等 2MSL**：

1. 保证最后一个 ACK 能到达服务器（如果 ACK 丢了，服务器会重发 FIN，客户端还能再回一次 ACK）。
2. 让本次连接中滞留的旧报文在网络中消失，避免影响下一次同端口的新连接。

MSL 是报文最大生存时间，2MSL 就是一去一回的上限。

## 7.6 常见易错点

1. **端口是传输层的概念**，IP 是网络层的；「IP + 端口」才定位到进程。
2. UDP 首部 8 B，TCP 首部 20 B（不含选项）。
3. **SYN 和 FIN 都占 1 个序号**，所以 `ack = seq + 1`。
4. 三次握手第三次可以携带数据；前两次不能带数据。
5. TIME_WAIT 出现在**主动关闭方**，不是被动方。
6. `RST` 是异常重置，不是正常关闭。

## 7.7 自测

<details>
<summary>Q1：为什么 TCP 需要三次握手而 UDP 不用？</summary>

UDP 无连接、不保证可靠，直接发就行；TCP 要保证可靠传输，必须先确认双方收发能力都正常，还要同步初始序号。
</details>

<details>
<summary>Q2：ACK 报文段本身要占序号吗？</summary>

不占。纯 ACK 不带数据时序号字段不变，但 SYN 和 FIN 这两个控制位各占一个序号。
</details>

<details>
<summary>Q3：为什么关闭要四次，而建立只要三次？</summary>

建立时服务器的 SYN 和 ACK 可以合在一个报文里发；关闭时一方发 FIN 后，另一方可能还有数据没发完，只能先回 ACK，等发完再发 FIN，所以拆成两次。
</details>

<details>
<summary>Q4：TIME_WAIT 的两个作用是什么？</summary>

① 保证最后一个 ACK 能被对方收到（丢了可重发）；② 让旧连接的残留报文在网络中过期，不影响新连接。
</details>

<details>
<summary>Q5：UDP 校验和里的伪首部包含什么？</summary>

源 IP、目的 IP、协议号、UDP 长度（共 12 字节），加它是为了顺带校验 IP 地址是否被改错；伪首部不实际传输。
</details>
