

[[浮点数]]的精度问题本质上源于**计算机用二进制存储数据**的特性，以及**有限的存储空间**对数值表示的限制。具体来说，主要有两个核心原因：

### 1. 二进制无法精确表示所有十进制小数

我们日常使用的是十进制（基数为 10），但计算机内部只能用二进制（基数为 2）存储数据。对于小数，并不是所有十进制小数都能被二进制精确表示 —— 就像十进制无法精确表示 1/3（0.3333... 无限循环）一样，二进制也有很多 “无法精确表达” 的十进制小数。

例如，十进制的 `0.1` 转换为二进制是一个**无限循环小数**：

`0.1₁₀ = 0.00011001100110011...₂`（“0011” 无限循环）。

但计算机存储[[浮点数]]时，用于表示小数部分的位数是**有限的**（比如 `float` 有 23 位，`double` 有 52 位），超出的部分会被截断或四舍五入，导致存储的是一个近似值而非精确值。

### 2. [[浮点数]]的存储结构限制了精度

现代计算机遵循 **IEEE 754 标准** 存储[[浮点数]]，其结构分为三部分：

- **符号位**：表示正负（1 位）；
- **指数位**：表示数值的量级（如 `float` 8 位，`double` 11 位）；
- **尾数位**：表示数值的有效数字（如 `float` 23 位，`double` 52 位）。

其中，**尾数位的长度直接决定了精度**。例如：

- `double` 的尾数位是 52 位，加上默认的 “1.” 前缀，总共能表示约 **15-17 位十进制有效数字**；
- 超过这个范围的有效数字会被丢弃，导致精度损失。

这种 “有限位数” 的存储方式，使得[[浮点数]]本质上是**对真实值的近似**，而非精确表示。

### 典型例子：0.1 + 0.2 ≠ 0.3

正因为 `0.1` 和 `0.2` 在二进制中都是近似存储，它们的和在转换回十进制时，会出现微小的误差：

javascript

运行

```javascript
console.log(0.1 + 0.2);  // 输出 0.30000000000000004 而非 0.3
```

### 总结

[[浮点数]]的精度问题不是 “bug”，而是**二进制存储机制和有限存储空间共同导致的必然结果**。它提醒我们：在对精度要求极高的场景（如货币计算、高精度科学计算），应避免直接使用 `float` 或 `double`，而应使用专门的高精度类型（如 Java 的 `BigDecimal`、Python 的 `decimal` 模块）。
